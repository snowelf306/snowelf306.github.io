1. 核心概念：Git 到底在记什么

📸 快照，不是差异

每次 commit 保存的是整个项目的完整快照；未变动的文件只存一个指针。 这让「回到任意历史时刻」几乎零成本。

🔑 哈希即身份

每个提交有一个 40 位 SHA-1 指纹（终端里常显示前 7 位，如 a1b2c3d）。 内容变一个字节，指纹就完全不同 —— 因此历史无法被悄悄篡改。

🌐 分布式全量仓库

clone 下来的不是「一份副本」，而是包含全部历史的完整仓库。 断网也能提交、查日志、建分支；push 只是同步。

文件的三种状态

Modified 已修改改了，但还没保存到仓库
→
Staged 已暂存标记了，下次提交会带上它
→
Committed 已提交已安全落盘到本地仓库

💡 新手最大的困惑几乎都来自「暂存区」这个中间层。它存在的意义是：让你把一堆乱七八糟的改动， 挑选出逻辑完整的一小块再提交 —— 而不是「一次性全交」。记住：add 是拍照，commit 是冲印成册。

3. 日常命令：从安装到提交

0

初次配置（每台机器一次）

作者信息会被写进每个提交。--global 写入用户级配置，单个仓库可用 --local 覆盖。

git config --global user.name  "你的名字"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.autocrlf input   # Windows 建议 true，macOS/Linux 用 input
git config --list                          # 查看当前生效配置
1

创建仓库 / 获取仓库

git init                 # 把当前目录变成 Git 仓库（只是多出一个 .git 目录）
git clone <url>          # 克隆远程仓库，含全部分支与历史
git clone -b dev --depth 1 <url>   # 只要 dev 分支最近 1 次提交：CI 提速常用
2

核心循环（每天都要用）

git status               # 万能第一步：现在到底什么状态
git add app.js           # 暂存单个文件
git add -p               # 逐块(hunk)挑选要暂存的改动，强烈推荐
git diff                 # 工作区 vs 暂存区：还没 add 的改动
git diff --staged        # 暂存区 vs 仓库：即将提交的内容
git commit -m "feat: 支持批量导入"
git commit -am "fix: 修正空指针"   # -a 自动暂存「已跟踪」文件的改动（不含新文件）
3

查看历史

git log --oneline --graph --decorate -20
git log --author="张三" --since=2.week.ago -p
git show HEAD            # 某次提交的完整差异
git blame app.js         # 每一行是谁、在哪次提交写的
git tag -a v1.0 -m "release"     # 给提交打标签
4

.gitignore：别把垃圾提交进去

# 依赖与构建产物
node_modules/
dist/
*.log
# 本地配置与密钥（密钥绝不进仓库）
.env
.env.local
# 系统 / 编辑器
.DS_Store
.idea/
# 例外规则：感叹号放在后面覆盖前面的规则
!dist/keep.txt

⚠️ .gitignore 只对未被跟踪的文件生效。已经提交过的文件要这样移除： git rm -r --cached node_modules（保留本地文件，只停止跟踪），然后提交。

5

写一条好的提交信息

feat: 新增 CSV 批量导入
fix: 修复分页越界导致的 500
docs / style / refactor / perf / test / chore   # 常用类型前缀
格式约定：类型: 一句话说明「做了什么」，空一行后写「为什么这么做」。 判断标准很简单 —— 半年后你 git log 时，只看这一行能不能想起当时为什么改。 不要用「update」「修改bug」这类信息，它们等于没写。

4. 分支实验室：边玩边懂 HEAD

分支不是「复制一份代码」，它只是一个指向某次提交的可移动指针；HEAD 则告诉你「我现在在哪个分支上」。 所以下面创建分支是瞬间完成的，无论仓库有多大。

当前分支：main
已有分支：
HEAD 指向：refs/heads/main
试试这个练习：在 main 上提交 1 次 → 新建 feat 分支 → 提交 2 次 → 切回 main → 提交 1 次 → 合并 feat。 因为 main 前进了，这次合并无法快进（fast-forward），Git 会自动生成一个有两个父提交的 merge commit。

merge 还是 rebase？

维度git merge featgit rebase main（在 feat 上执行）
做了什么新建合并提交，把两条线接到一起，历史原样保留把 feat 的提交逐个「重放」到 main 之后，历史变成一条直线
历史长相真实、有交叉，能看出功能边界干净、线性，review 时更易读
提交哈希不变全部改变（等同重写历史）
冲突处理集中一次可能在每个重放提交上反复出现
黄金法则并入主干时用它更安全只对自己尚未推送（或只有自己在用）的分支使用；对已共享的分支 rebase = 给同事制造灾难

团队里常见的折中：功能分支内用 rebase 保持整洁，合入主干时用 merge --no-ff 保留功能边界。

5. 远程协作：push 之前先看清楚

git fetch

把远程的最新提交下载到本地的 origin/main，不改动你的工作区和当前分支。安全，随时可用。

git pull

= fetch + merge（加 --rebase 则是 fetch + rebase）。方便但会「自动改你的历史」，不熟时建议先 fetch 再自己决定。

git push

把本地提交上传。首次用 git push -u origin feat 建立跟踪关系，之后只需 git push。

git remote -v                          # 看远程别名与地址
git remote add upstream <url>          # fork 工作流：加原仓库
git fetch --all --prune                # 同步所有远程并清理已删除的远程分支
git branch -a                          # -a 含远程分支；本地 main 与 origin/main 是两回事
git checkout -b dev origin/dev         # 基于远程分支建本地分支（新 Git 可直接 git switch dev）

# 推荐的安全同步节奏
git fetch origin
git log --oneline HEAD..origin/main    # 别人有、我还没有的提交
git log --oneline origin/main..HEAD    # 我有、别人还没有的提交
git rebase origin/main                 # 或 merge，把上游改动接进来
git push                               # rebase 之后推送需 git push --force-with-lease

解决冲突的完整流程

冲突不是错误，而是 Git 说「这两处改动我无法自动判断，请你决定」。解决它永远是同四步：

  1. 定位：git status 会列出 both modified 的文件。
  2. 编辑：打开文件，处理冲突标记 —— 留下正确内容，把标记行整行删掉。
  3. 标记已解决：git add <file>（这一步就是告诉 Git「我处理好了」）。
  4. 收尾：git commit（merge）或 git rebase --continue（rebase）。中途想放弃：git merge --abort / git rebase --abort。

冲突时的帮手：git mergetool、VS Code 内置的「采用当前/采用传入/保留双方」按钮、 git config --global merge.conflictStyle zdiff3（会额外显示共同祖先，判断意图极有用）。 另外 git checkout --ours / --theirs <file> 可整文件选边站。

6. 协作工作流：GitHub Flow 与一次提交的生命周期

前面讲的是「一个人的 Git」。真正到了团队里，规则其实只有两条：① 主干（main）任何时刻都是可发布的；② 所有改动都通过分支 + Pull Request 汇入主干。 这套极简规则就是 GitHub Flow —— 它不是新命令，而是把第 4、5 节学过的分支与远程，套进一个可协作的节奏里。

① GitHub Flow 六步循环（点「下一步」走一遍）

1 / 6
GitHub Flow做什么常用命令 / 操作
1 开分支从 main 切出一个短命功能分支，分支名说清意图git switch -c feat/csv-import
2 提交本地小步提交，信息按规范写（见 ③）git add -p · git commit -m "feat: …"
3 保持同步main 前进了就把改动接进来，别攒到最后统一解决冲突git fetch · git rebase origin/main
4 推送分支把分支推到远端，成为可评审的公开备份git push -u origin feat/csv-import
5 开 PR + 评审请求合并；CI 跑测试，同事在 diff 上评论，你继续 push 同一分支即可自动更新 PRGitHub 界面 + 追加 git push
6 合并并删除分支通过后合入 main，立刻部署；功能分支使命结束Squash / Merge commit + 删分支

循环而不是瀑布：PR 合并后马上开始下一个功能分支，main 一直在前进、一直在可发布状态。这就是「持续交付」在 Git 层面的形态。

② 合并方式怎么选：Squash / Merge commit / Rebase merge

① Squash and merge

把 PR 里的 fix typo、wip 等 N 个提交压成 1 个进 main。主干历史 = 功能列表，最干净。

👉 大多数开源项目 / 小粒度 PR 的默认选择

② Create a merge commit

保留分支上每个提交 + 一个 merge commit，功能边界和过程都留下。

👉 一个 PR 本身就是一个完整里程碑、提交历史值得保留时

③ Rebase and merge

把 PR 的提交逐个搬到 main 之后，线性历史但保留细节；代价是哈希全变。

👉 团队要求「历史必须线性」；禁止在 main 上用

仓库管理员应在 Settings 里只勾选团队约定的一种，否则三年后 main 的历史会是三种风格搅在一起。 个人建议：Squash 为默认，同时把「一个 PR 只做一件事」作为团队纪律 —— PR 越小，squash 出来的提交就越是天然的功能单位。

③ 提交信息生成器（Conventional Commits 解剖）

规范只有一行格式：类型(范围): 一句话说清做了什么。点下面的按钮，边生成边看每个字段的作用 —— 生成结果可直接复制到真实项目。

7. 急救包：出事时先看这里

  
先记住一句保命话：只要东西被 commit 过（甚至只是 add 过），Git 几乎都能找回来；
  真正危险的是 reset --hard、clean -fd 和强制推送。慌了就先 git stash + git status。


  

    

      提交信息写错了 / 忘了加文件（仅限还没 push）
      

        
git add 漏掉的文件
git commit --amend -m "feat: 正确的描述"

        
--amend 会替换最后一次提交（生成新哈希）。已经推送给别人用过的提交不要 amend，改用 revert。

      

    


    

      工作区改乱了，想丢掉本次修改
      

        
git restore app.js              # 丢弃单个文件的未暂存修改
git restore .                   # 丢弃全部未暂存修改（危险）
git clean -nd                   # 先看会删掉哪些「未跟踪」文件（dry-run，务必先跑）
git clean -fd                   # 再真删；-x 连 .gitignore 忽略的也删

        
未跟踪的新文件不在任何提交里，clean 之后无法找回。拿不准就先 git stash -u。

      

    


    

      add 多了，想从暂存区拿回来
      

        
git restore --staged app.js     # 取消暂存，工作区改动完整保留
git reset                       # 取消全部暂存（旧写法，同样安全）

      

    


    

      想回退到之前的某次提交（三种 reset 的区别）
      

        

          

            
命令仓库 HEAD暂存区工作区文件典型用途

            
              
reset --soft HEAD~1回退保留保留把几次提交合成一次再写信息

              
reset --mixed HEAD~1（默认）回退清空保留重新挑选要提交的文件

              
reset --hard HEAD~1回退清空丢弃彻底不要了（可用 reflog 救）

              
revert <sha>前进—反向改动已推送的提交：用一个新提交抵消它

            
          

        

      

    


    

      handy：切分支时改动放不下（stash）
      

        
git stash push -u -m "半成品：导入功能"   # -u 连未跟踪文件一起收走
git switch main
git stash list
git stash pop                     # 恢复并删除该条
git stash apply stash@{1}         # 恢复但保留
git stash drop stash@{0}

      

    


    

      提交到了错误的分支
      

        
git log --oneline -3              # 记下错误的提交哈希 abc1234
git switch correct-branch
git cherry-pick abc1234           # 把它摘过来
git switch wrong-branch
git reset --hard HEAD~1           # 确认无误后再清掉原处的误提交

      

    


    

      已经把东西删没了 —— 用 reflog 找回
      

        
git reflog                        # HEAD 的所有移动记录，包括被 reset 掉的提交
# 输出如：HEAD@{2}: commit: 那个被我删掉的功能
git diff HEAD@{2}                 # 先看看那次提交是什么
git reset --hard HEAD@{2}         # 或 git cherry-pick HEAD@{2} 只取那一次

        
只要还没被 gc 回收（默认至少保留 30 天），本地历史基本都在。先 git branch backup 做个保险再折腾是好习惯。

      

    


    

      进入 (HEAD detached) 分离头指针状态
      

        
常见于 checkout 到某个标签或哈希。此时提交不属于任何分支，切走就「看不见」了。

        
git switch -c fix-from-tag        # 立刻把当前提交挂到新分支上（最常用）
git switch main                   # 不需要这些提交就切回去

      

    


    

      大文件 / 密钥不小心提交了
      

        
git rm --cached secrets.env       # 停止跟踪，本地文件保留
echo "secrets.env" >> .gitignore
git commit -m "chore: 移除不应入库的文件"

        
注意：文件仍留在历史里。真正的清理要 git filter-repo（或 BFG）重写历史 + 强制推送，
        且密钥必须立刻作废重发 —— 只要推送过，就应视为已泄露。
